# 서울교통공사 상수도 관리

React/Vite 화면 + FastAPI API + SQLite 계정·계량기 관리. 하드웨어 연동 없이 아리수 청구·일 사용량과 서울교통공사 승하차 자료를 관리합니다.

## 폴더 구성

| 경로 | 역할 |
|---|---|
| `front/` | 현재 웹 화면 |
| `back/api/`, `back/pipelines/` | API, 계정·계량기 관리, 실제 수집·모델 갱신 |
| `back/scripts/`, `back/ml/lightgbm/` | 운영 수집 도구·공유 ETL 함수·현재 모델 코드 |
| `data/app_seed/`, `data/processed/`, `data/ml_dataset/`, `data/billing/` | 초기 앱 자료, 재사용하는 정제 자료·학습 자료·계량기 매핑 |
| `data/runtime/` | 비공개 운영 DB, 수집 결과, 모델 결과, 스냅샷의 기본 위치 |
| `archive/` | 이전 실험, 사용하지 않는 ETL·크롤러, 과거 원자료·결과 |

과거 파일은 원래 경로 구조를 유지해 [archive/README.md](archive/README.md)에 정리했습니다. 현재 앱은 `archive/`를 읽지 않습니다. 초기 위험도 자료는 `data/app_seed/risk/test_anomalies.csv`를 사용합니다. `.env`와 운영 DB·수집 캐시는 보관 폴더로 이동하지 않습니다.

## 설치 및 실행

Python 3.11 이상, Node.js 20.19 이상(또는 22.12 이상)이 필요합니다. 저장소 루트에서 실행합니다.

```sh
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-dev.txt
npm install
```

conda를 쓴다면 venv 대신 `conda env create -f environment.yml && conda activate hanul`(기존 `hanul` 환경은 `conda activate hanul && python -m pip install -r requirements-dev.txt`) 후 `npm install`합니다. `npm run dev:api`·`start`는 현재 활성화된 환경의 `python`을 사용하므로 실행 전 환경을 활성화하세요. 아래 `source .venv/bin/activate`도 `conda activate hanul`로 바꿔 실행합니다.

macOS에서 LightGBM이 `libomp.dylib`을 찾지 못하면 `brew install libomp`, Ubuntu에서는 `sudo apt-get install libgomp1` 후 다시 실행합니다. 모델 학습 없이 API와 화면만 시험한다면 `back/api/requirements.txt`만 설치해도 됩니다.

`.env`가 없을 때만 `.env.example`을 복사합니다. 기존 파일의 값은 보존하고 새 항목만 추가하세요.

```sh
cp .env.example .env
```

먼저 `ADMIN_EMAIL`, `ADMIN_PASSWORD`(12~128자)를 채웁니다. 사용자 DB가 비어 있을 때 첫 총괄 관리자를 생성하며 첫 로그인 후 비밀번호를 변경해야 합니다. 이후 `.env` 수정으로 기존 비밀번호가 덮어써지지는 않습니다. 초기 설정이 끝나면 운영 환경의 `ADMIN_PASSWORD` 값을 제거합니다. 로그인 후 관리 화면에서 직원을 확인해 담당자 계정을 등록합니다. 공개 회원가입은 없습니다.

```sh
# 터미널 1: API
npm run dev:api
# 터미널 2: 화면
npm run dev
```

`http://127.0.0.1:5173`에서 로그인합니다. 프론트 개발 서버는 `/api`를 8000번 API로 전달합니다. 화면은 1분마다 자료를 다시 확인하지만, 바뀐 것이 없으면 서버가 본문 없이 응답하므로 전체 자료를 다시 받지 않습니다. OpenAI/SMTP/수집 키가 없어도 기존 자료와 로그인·계량기 관리·통계·PDF·Excel을 시험할 수 있습니다.

```sh
# 빌드 후 API 하나로 화면과 데이터를 서비스
npm run build
npm run start
# http://127.0.0.1:8000
```

운영에서는 HTTPS를 적용하고 `APP_ENV=production`, `APP_COOKIE_SECURE=true`, `APP_ORIGINS`, `APP_ALLOWED_HOSTS`를 실제 도메인으로 지정합니다. API 서버와 수집 명령은 같은 `APP_DATA_DIR` 및 `APP_DB_PATH`를 사용해야 합니다. 기본 저장소는 `data/runtime/`입니다. 이 디렉터리는 사용자/세션/수집 자료를 포함하므로 외부 정적 웹서버에 노출하지 않습니다. `front/dist/`만으로는 로그인 데이터 서비스를 제공할 수 없습니다.

### EC2·RDS·S3 배포 상태

계획한 규모는 EC2 `t3.medium`(4GiB, gp3 50GB), RDS PostgreSQL `db.t4g.small`(Single-AZ, gp3 20GB), 비공개 S3 50GB입니다. **현재 코드로는 이 구성을 그대로 배포할 수 없습니다.** `back/api/db.py`와 여러 API·수집 쿼리가 SQLite 전용이며, `APP_DB_PATH`에 PostgreSQL 주소를 넣어도 연결되지 않습니다. RDS 사용 전 스키마·트랜잭션·쿼리·백업 명령·일회성 데이터 이관을 수정하고 PostgreSQL 통합 시험을 끝내야 합니다. 그때까지 아래 SQLite 백업 명령은 현재 구현에만 해당합니다.

- EC2의 전용 일반 사용자로 `npm run start:production`을 사용해 API **한 인스턴스**를 실행하고, HTTPS 역방향 프록시가 화면과 `/api`를 같은 도메인으로 전달하게 합니다. Uvicorn은 `127.0.0.1:8000`에만 바인딩합니다. 프록시는 실제 `Host`와 `X-Forwarded-Proto`를 전달하고, 외부 요청을 직접 받는 Nginx라면 `X-Forwarded-For`를 `$remote_addr`로 덮어씁니다. 실행 명령은 로컬 프록시만 신뢰합니다. 로그인 경로에 프록시의 IP별 요청·동시 연결 제한을 두고, 8000번 포트는 외부에 열지 않습니다.
- 운영 설정은 `APP_ENV=production`, `APP_COOKIE_SECURE=true`, `APP_ORIGINS=https://water.example.com`, `APP_ALLOWED_HOSTS=water.example.com`, `APP_DATA_DIR=/var/lib/water-monitor`, `TODAY_OVERRIDE=`처럼 실제 도메인과 경로를 지정합니다. **현재 SQLite 구현에서** `APP_DB_PATH`의 기본값은 `/var/lib/water-monitor/app.sqlite3`입니다. 운영 데이터·DB 경로가 저장소 안이거나 HTTPS/쿠키/호스트 설정이 잘못되면 서버 시작을 중단합니다. 환경 파일은 저장소 밖에 0600 권한으로 두고 systemd `EnvironmentFile` 등으로 프로세스에 주입합니다. `APP_ENV=production`으로 시작하면 저장소의 개발용 `.env`는 읽지 않습니다.
- 수집 원본·모델 결과는 먼저 EC2의 암호화된 영속 EBS에서 처리합니다. 현재 수집기는 로컬 파일 잠금과 원자적 파일 교체를 사용하므로 S3를 `APP_DATA_DIR`로 지정하거나 마운트하지 않습니다. EBS 디렉터리는 전용 사용자 소유·0700 권한으로 두고 기존 파일 권한도 확인합니다. 파일 백업은 수집·모델 갱신이 끝난 일관된 시점에 S3로 업로드합니다. 자동 S3 업로드·복구 절차는 아직 구현되지 않았습니다.
- S3 버킷은 Block Public Access, 기본 암호화, 버전 관리와 오래된 버전의 수명 주기를 설정합니다. EC2 인스턴스 역할에 해당 백업 prefix의 최소 권한만 부여하고 장기 AWS 액세스 키를 환경 파일에 저장하지 않습니다. PostgreSQL 이관 후 DB 복구는 RDS 자동 백업·스냅샷으로 관리하고, S3에는 파일 자료를 백업합니다.
- API는 1MB를 넘거나 길이를 밝히지 않은 요청 본문을 읽지 않고 거부하며, 화면 응답에는 같은 출처의 자원만 허용하는 CSP를 붙입니다. 프록시에서도 본문 크기를 제한하세요.
- EC2 보안 그룹에는 80/443만 공개하고 SSH는 관리 주소로 제한하거나 Session Manager를 사용합니다. RDS는 비공개 서브넷에 두고 5432는 EC2 보안 그룹에서만 허용합니다. EC2 메타데이터는 IMDSv2 필수로 설정합니다. 수집·AI·SMTP 비밀값은 서버 환경에만 주입합니다. AI 원인 추정은 역명과 사용량 이력을 외부 서비스로 전송하므로 데이터 반출 기준을 확인합니다.
- `t3.medium`에서는 모델 재학습과 API·수집 작업이 CPU·메모리를 공유합니다. 초기에는 모델 작업을 비혼잡 시간에 `--jobs 1`로 실행하고 실제 최대 메모리·CPU 크레딧·디스크 증가량을 확인합니다. Single-AZ RDS의 장애·복구 목표와 백업 보존 기간도 운영 전에 정합니다.
- GitHub 저장소를 비공개로 바꾸더라도 과거 공개 이력에 있던 청구·주소 자료의 노출은 되돌릴 수 없습니다. 해당 자료가 실데이터라면 이미 복제되었을 가능성을 전제로 접근 권한과 보존 범위를 별도로 검토합니다.

## 사용 흐름

- **총괄 관리자**: 모든 사업소 열람, 담당자 생성·비활성화·비밀번호 재설정, 계량기 관리. 마지막 활성 총괄 관리자는 비활성화할 수 없습니다.
- **사업소 담당자**: 배정된 사업소 자료와 계량기만 관리. 사업소별 활성 담당자는 최대 2명입니다. 계정 비활성화·권한 변경·비밀번호 재설정 시 기존 세션은 만료됩니다.
- **계량기**: 역/호선/고객번호/표시명/직원·시민 등 사용 목적/요금 업종/사업소를 별도로 관리합니다. 신규 계량기는 이력이 없어도 표시됩니다. 비활성화는 과거 청구·사용량을 삭제하지 않습니다. 고객번호 변경은 새 계량기로 등록합니다.
- **삭제·복원**: 삭제하면 관제·통계·수집 대상에서 빠지고 삭제 목록으로 이동합니다. 기존 청구·관측은 보존하며 복원하면 다시 조회할 수 있습니다. 수집 중인 계량기는 작업 완료 후 삭제·수정합니다. 같은 고객번호는 중복 등록하지 않고 기존 계량기를 업데이트하거나 복원합니다.
- **청구 전용 구분**: 실제 일일 사용량이 있는 계량기만 일일 관제와 주의·경고 대상입니다. 청구서만 있는 계량기는 청구 이력·월별 비교·PDF·청구 Excel을 제공합니다. 일일 수집을 켠 신규 계량기는 첫 자료 수집까지 별도 수집 대기로 표시합니다. 같은 역 안에서도 계량기별로 구분합니다.
- **지도와 상세**: 같은 물리역에 여러 호선·계량기가 있으면 개별 선택합니다. 지도 좌표가 없는 역도 목록에서 조회할 수 있습니다. 위치는 총괄 관리자가 조정할 수 있습니다.
- **청구**: 월과 정기분/수시분을 구분합니다. PDF 열람·인쇄·다운로드와 Excel 내보내기는 API에서 권한을 다시 확인합니다. PDF는 수집된 값으로 생성한 **수도요금 조회내역**이며 아리수 원본 고지서 PDF가 아닙니다. 원본 출력 경로는 실제 계정으로 확인 후 별도로 연동해야 합니다.
- **통계**: 일 사용량은 관측일, 요금은 청구월 기준으로 집계합니다. 누락은 0과 구분하며 청구 주기를 임의로 월 단위로 나누지 않습니다.
- **이상 요약**: 화면과 API가 같은 분석 결과를 사용합니다. 다른 날짜의 결과로 대체하지 않습니다. OpenAI 원인 추정은 실제 사실과 구분하며, 실패하면 그 상태를 표시합니다.
- **메일**: 알림 버튼을 누를 때만 발송합니다. 수신자는 해당 사업소의 활성 담당자로 서버가 결정합니다. 같은 항목은 1분에 한 번, 계정당 한 시간에 30회까지 보낼 수 있습니다. SMTP 미설정/실패는 발송 성공으로 표시하지 않습니다.

초기 자료는 `data/app_seed/`에서 비공개 DB로 한 번 가져옵니다. 기존 청구 JSON, 제공된 상세 CSV의 합집합을 보존하고 중복 기준은 계량기+청구월+청구구분+고지번호입니다. 별도 고지번호가 없는 기존 청구서는 기존 ID를 유지합니다. 서버 재시작 시 관리자가 수정한 등록정보를 덮어쓰지 않습니다. 원본 자료/발표자료는 변경하지 않습니다. `meter_collection.csv`는 제공된 3차검토(260518) Excel의 D열 고객번호·F열 고지서상 성명·J열 유무(O)를 옮긴 등록 368개의 초기 수집 설정입니다. 일일+청구 81개, 청구 전용 287개이며 최초 적용 이후 관리자 변경을 보존합니다.

## 실제 자료 갱신

`.env`의 `ARISU_USER_ID`, `ARISU_USER_PWD`를 설정하고 서버를 재시작하면 웹 화면의 **정보 업데이트**로 수집할 수 있습니다. 총괄은 전체 계량기, 담당자는 배정된 사업소만 실행·조회합니다. 개별 계량기도 바로 업데이트할 수 있습니다.

- 신규 아리수 계량기 등록·복원 시 고객번호로 연결 확인 작업을 자동 예약합니다. 설정 누락, 인증 실패, 조회 권한 필요, 조회 결과 없음, 일부 성공을 구분합니다. 빈 결과만으로 존재하지 않는 고객번호라고 단정하지 않습니다. 아리수가 실제 반환한 고객번호도 대조합니다.
- 청구서는 아리수 **요금조회 및 납부 → 전체보기**에서 고객번호와 정확한 고지서상 성명으로 수집합니다. 계정 고객번호 등록은 필요하지 않습니다. 월별 목록과 상세 요금·사용기간·검침·지하수 항목을 저장하며 성명 불일치는 별도로 안내합니다. 일일 검침에만 계정의 고객번호 등록·조회 권한이 필요합니다. 아리수의 고객번호 등록을 자동 변경하지 않습니다.
- 관리 화면에서 **청구서만 / 일일 사용량 및 청구서**를 선택합니다. 청구 전용은 일일 조회·위험도에서 제외하며 자동 전환하지 않습니다. 일일 조회가 실패해도 청구서를 별도로 수집합니다. 정상 사용량 0톤과 자료 없음은 다르게 취급합니다.
- 음수·빈 검침값은 해당 날짜만 제외하고 정상 날짜는 보존합니다. 제외 일자는 수집 결과에서 확인할 수 있습니다. 양수 사용량을 임의 상한으로 버리지 않습니다.
- 기본 자동 수집은 **매일 오전 8시(한국시간)**입니다. 총괄 관리자가 켜기·끄기·시각을 변경할 수 있습니다. 서버가 켜져 있어야 하며, 꺼져 있던 경우 재시작 후 해당 날짜의 미실행 작업을 한 번 예약합니다. 아리수 로그인 설정이 없어도 고지서상 성명이 있는 청구서는 수집할 수 있습니다.
- 기존 일일 이력의 빈 날짜와 최근 3개월을 월별로 재조회합니다. 신규 계량기는 최근 12개월을 확인합니다. 과거의 빈 월은 주 단위로 다시 확인하며, 최근 청구 및 이력 사이의 누락 기간을 보충합니다. 과거 확정 검침과 최신 미결산 검침을 함께 조회하고 오늘의 미완성 자료는 제외합니다. 갱신 지연·정정에 대응해 최근 구간은 이미 저장된 날도 확인하지만 중복 저장하지 않습니다.
- 작업은 서버에서 이어서 처리하며 화면을 닫아도 계속됩니다. 진행 건수·계량기별 결과·마지막 성공 시각을 표시합니다. 서버 중단으로 끊긴 작업은 중단 상태로 남으며 **정보 업데이트**로 재시도합니다. 삭제·비활성 계량기는 제외하고 수집 실패로 기존 자료를 지우지 않습니다.

이 버튼은 아리수 청구·관측 갱신입니다. **승하차 수집과 모델 재학습은 아래 관리 명령으로 실행합니다.** 새 관측을 가져왔다고 과거 분석을 새 분석으로 표시하지 않으며 화면에서 사용량·위험도 기준일을 구분합니다. 승하차 수집에는 `SEOUL_PSGR_KEY`가 추가로 필요합니다. 아래 날짜는 예시이므로 필요한 범위로 바꾸세요.

```sh
source .venv/bin/activate
python -m back.pipelines.refresh --start 2026-05-01 --end 2026-09-22 --all
# 작은 범위부터 외부 연결 확인
python -m back.pipelines.refresh --start 2026-09-20 --end 2026-09-22 --water --ridership
# 청구만 갱신 / 저장된 자료로 모델만 다시 실행
python -m back.pipelines.refresh --start 2026-06-01 --end 2026-09-22 --bills
python -m back.pipelines.refresh --model
```

승하차 일별 API는 최근 1주일치만 제공합니다. 그보다 오래된 날짜는 서울 열린데이터광장의 월별 파일(OA-12914, 인증키 불필요)로 채웁니다. 월별 파일은 그 달이 지난 뒤에 올라옵니다.

```sh
python -m back.pipelines.daily_ridership.monthly 2026-05 2026-08
```

계량기 등록부에서 활성화한 아리수 고객번호만 수집합니다. 위 CLI의 `--water`와 `--ridership`은 일일 수집 대상으로 확인된 계량기를 사용합니다. 웹 정보 업데이트도 등록부에서 선택한 수집 범위를 따릅니다. 타 수도사업자 고객번호는 등록·조회 가능하지만 아리수 수집에는 보내지 않습니다. 아리수에서 해당 고객번호 조회가 가능한지는 실제 계정으로 확인해야 합니다.

수집 성공 행은 보존하고 실패 대상을 재시도할 수 있습니다. 결과와 오류는 `data/runtime/refresh_report.json`에 기록되며 오류 발생 시 명령은 실패 코드로 끝납니다. API는 완성된 snapshot manifest를 통해 자료를 읽습니다. 수집 원본·계정·청구 데이터를 GitHub Pages나 공개 데이터 브랜치에 게시하지 않습니다. 자동 실행 설정은 `back/pipelines/README.md`를 참고하세요.

모델은 CPU에서 실행하며 시간 순서에 따라 학습/검증/평가합니다. 구간 경계는 `--train-end`, `--valid-end`로, 평가 구간의 끝은 `--test-end`로 정합니다(예: `python -m back.pipelines.refresh --model --train-end 2026-01-28 --valid-end 2026-05-13 --test-end 2026-08-31`). 경계를 생략하면 직전 실행의 경계를 그대로 쓰므로, 매일 수집 뒤 `python -m back.pipelines.refresh --model`만 돌리면 같은 분할로 다시 학습해 수집된 마지막 날까지 판정합니다. `--test-end` 이후의 관측은 평가에서만 빠지고 화면에는 그대로 표시됩니다. 당일·전날 승하차가 아직 없는 날은 승하차 없이 학습한 보조 모델로 판정합니다(`test_anomalies.csv`의 `without_ridership`). 신규 계량기의 학습·검증 이력이 부족하면 자료 부족으로 남기고 임의의 정상 판정을 만들지 않습니다. 회의 자료의 사용량 증감 임계치에는 주의/경고 수치가 상충해 별도 운영 규칙으로 확정하지 않았습니다. 현재 표시되는 ML 심각도는 기존 모델 설정에 따른 값입니다. 예측은 같은 날 다른 역들이 함께 움직인 만큼 보정하므로(자기 검침값은 제외) 그날 다른 역의 검침값이 6곳 이상 있어야 보정이 적용됩니다. 심각도는 오차를 그 역의 최근 28일 사용량에 견준 비율로 정하며, 학습한 모델은 `data/runtime/model/model.txt`에 저장됩니다.

```sh
source .venv/bin/activate

```

테스트는 외부 서비스 대신 고정 응답과 임시 DB를 사용합니다. 익명 접근, 사업소 간 접근 차단, PDF/Excel 권한, CSRF, 비밀번호·세션 해제, 담당자 수 제한, 신규 계량기 빈 이력, 수집 부분실패와 재실행, 청구 병합, 한국어 PDF 등을 검사합니다.

## 저장·백업

운영 DB와 `data/runtime/`를 비공개 디스크에 유지하세요. 실행 중 SQLite 파일 하나만 복사하지 말고 SQLite backup API를 사용합니다.

```sh
python -m back.api.manage backup /private/backup/water.sqlite3
# 관리자 비밀번호를 잊은 경우: 서버 운영자가 터미널에서 안전하게 입력
python -m back.api.manage reset-password admin@example.com
```

퇴사자는 계정을 비활성화하고 사업소 담당자를 교체합니다. API 응답·PDF·내보내기는 저장소의 현재 사업소 권한을 검사합니다. 원자료가 포함된 저장소 자체의 접근 권한도 조직 내부로 제한해야 합니다.
